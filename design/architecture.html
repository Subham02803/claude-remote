claude-remote · technical design

How it works inside

Plain English, for the version we are about to build. We drive the real claude command in a real terminal — no SDK, no API key — so the work comes out of the Max subscription instead of metered credits.

Companion to docs/01-product-scope.md (what it is for), docs/02-security-model.md (how access is controlled), docs/03-implementation-plan.md (the order we build it), and design/prototype.html (what it looks like).

1. The shape of it

There are two paths between your thumb and your code, and understanding the design is mostly understanding why there are two.

The down path carries a terminal: bytes from Claude Code to your screen, keystrokes back. The up path carries facts — Claude Code's own hooks POST to our server to say blocked, finished, failed. One path is for looking, the other is for knowing.

Grey is the terminal, amber is the knowing. Claude Code talks to us the same way it would talk to any other tool on the machine — through its own hook system — so we never have to guess at meaning by reading the screen.

Why the terminal, and not the Agent SDK The SDK is the tidier programming interface, and it was the first design in this file. It bills to metered API credits. The claude command is already signed in to the Max plan, so running it remotely costs exactly what running it at the desk costs — nothing extra. That single fact decided the architecture, and everything below is downstream of it.

2. What a session actually is

A session on the screen is a tmux session on the machine. That is the whole definition, and almost every durability requirement in the scope document falls out of it for free. 

# starting one — detached, in the project folder, running claude
tmux new-session -d -s cr-<id> -c ~/projects/web-dashboard claude

# what node-pty actually spawns when a browser connects
tmux attach -t cr-<id>

We never spawn claude directly. Going through tmux is the difference between a session that dies when a socket drops and one that does not notice.

P2 and UC-8 for free. "Never lose a session" and "pick up on my laptop what I started on my phone" are the same operation — reattaching — and neither is code we have to write.

The screen saysUnderneath that is
A sessionA tmux session named cr-<id>
The terminalA real PTY, rendered by xterm.js
The scrollbacktmux's own — we store none of it
Waiting on youA PermissionRequest hook that fired and has not been answered
ApproveA keystroke written into the PTY
StopCtrl-C, or tmux kill-session for the hard version
Who is the source of truth tmux list-sessions decides what exists. SQLite stores only what tmux cannot hold — which project a session belongs to, its title, which device started it. On boot we reconcile: a tmux session with no row is adopted, a row with no tmux session is marked ended. Two registries that can disagree is a bug factory, so one of them has to win, and it is tmux.

3. How we know what is happening

The obvious failure mode of a terminal bridge is that you only get bytes, and end up writing regular expressions against a TUI to guess whether Claude is blocked. We do not do that. Claude Code has a hook system, hooks can be type: "http", and so Claude Code simply tells us. 

// a hook that POSTs to us instead of running a script
{
  "hooks": {
    "PermissionRequest": [{
      "hooks": [{ "type": "http", "url": "http://127.0.0.1:4180/api/hooks" }]
    }]
  }
}
HookWhat it tells usDrives
SessionStartClaude's session_id and transcript_pathLinking a tmux session to a Claude session
PermissionRequestBlocked — plus tool_name and tool_inputThe banner, the badge, the push
PostToolUsetool_name, tool_input, tool_resultThe Changes tab; clearing the block
StopFinished, with last_assistant_messageDone state
StopFailureDied — matchable by type, including rate_limitFailed state, and the second push
SessionEndGone, and whyCleanup

Every payload also carries transcript_path — the session's JSONL on disk. That is where the Changes tab gets real file history from, without parsing a single escape sequence.

The mapping trap cwd is not a unique key — two sessions can run in the same folder, and scope UC-10 explicitly wants that. Capture Claude's own session_id at SessionStart and map on it. Getting this wrong means one session's approval prompt appearing on another session's screen.

4. The approval round-trip

The thirty-second unblock — UC-1, the reason the product exists. Two channels cooperate: the hook tells us that a decision is needed, and the keystroke delivers it.

The hook signals; the keystroke decides. Both are needed — the hook so your phone can buzz without you watching, the keystroke because the TUI is what actually owns the answer.

Why the hook does not make the decision

Hooks can return a permissionDecision, which looks like a tidier design: let the hook block until the phone answers. It is a trap. Hooks have a timeout. Parking one for the twenty minutes you spend on a bus would hit it and resolve as something you did not choose.

So the terminal keeps ownership of the answer and the hook is a doorbell. It also means the desktop path — just typing 1 into the terminal like you always have — keeps working, with nothing special about it.

Never leave a live button pointing at a moved-on terminal The Approve button writes a keystroke blind. It must render only while a PermissionRequest is genuinely outstanding, and must clear on PostToolUse or PermissionDenied. A stale button that types 1 into a prompt that has already advanced is answering a question nobody asked.

One more thing to settle by looking rather than remembering: which keys the current permission prompt accepts. Open it, read it, write it down. Do not hardcode from memory.

5. What the browser and server say to each other

One socket for the terminal, plain REST for everything with an answer, and one inbound endpoint that is not for the browser at all.

RouteWhat it does
WS /api/terminal/:idOutput bytes down; keystrokes and cols/rows up.
POST /api/hooksClaude Code posts here, not the browser. Loopback only.
GET /api/projectsDeclared project folders. Config, not discovery.
GET /api/sessionsThe overview. Reconciled from tmux list-sessions.
POST /api/sessionsNew tmux session in a project.
POST /api/sessions/:id/keysWrite a keystroke — how Approve and Deny work.
POST /api/sessions/:id/stopCtrl-C, or kill the session.
POST /api/push/subscribeRegister a device for the two notifications.
Rule R1 — the one test to write first The host guard is an onRequest hook covering every HTTP route. Verify by test that it also runs on the WebSocket upgrade. SameSite does not protect WebSocket handshakes and WebSocket has no CORS — and this socket is a terminal, so a page that slips past the check gets a shell, not a permission prompt. Write that test before the socket works.

7. A session's life

Every transition is a hook, not a guess. Which is the point of §3 — scope P6 demands that working / waiting / done / failed is never ambiguous, and a regular expression over a TUI could never honestly promise that.

8. Being told things

Only two events interrupt you: blocked (PermissionRequest) and failed (StopFailure). Everything else waits until you look. Scope §10 names notification fatigue as a real risk, so this is a design constraint rather than a preference.

Web Push needs a service worker, and a service worker needs a secure context. That is what tailscale serve is for, and why plain HTTP on the tailnet address is the lesser option.

9. What this design costs

Worth stating plainly once, because the honest description of the product changed when we chose the terminal.

A terminal in a browser is a shell, not a remote control for Claude. Claude Code always had a Bash tool, but a permission prompt sat in front of it. A raw PTY does not, and ! runs shell commands directly. With no sign-in, any device on your tailnet has a full shell as you.

Two things follow, and both are already reflected in the security model:

  • The tailnet gate now does all of the security work. The Host/Origin guard matters more, not less.
  • The old rule "confine Claude to declared project directories" is not enforceable at the app layer any more. cwd on the tmux session is a convenience, not a boundary — and the documents say so rather than pretending otherwise.

10. Things we are deliberately not doing

  • No Agent SDK and no API key. The subscription is the point.
  • No scraping the TUI for state. Hooks or nothing. If a hook cannot tell us something, we do not display it.
  • No storing scrollback. tmux already has it, and two copies would disagree.
  • No second process. One Fastify owns the PTYs; tmux owns durability.
  • No --dangerously-skip-permissions. The permission prompt is the last gate that still exists.
